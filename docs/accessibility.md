# 웹 접근성 — 시각장애가 있는 방문자도 쓸 수 있나요?

> **IT 담당자용 문서입니다. 고객은 읽지 않아도 됩니다.**

기준: **KWCAG 2.2(한국형 웹 콘텐츠 접근성 지침) / WCAG 2.1 AA**
검사일: 2026-09-16 · 검사 도구: axe-core 4.10.2 · 검사 명령: `node tools/check-a11y.mjs`

---

## 한 줄 답

**설정 마법사와 방명록 화면(우리가 만든 부분)은 기준을 지킵니다.
그러나 방문자가 실제로 글씨를 넣는 「작성 화면」은 이폼사인이 만드는 부분이고,
그 화면의 입력칸에는 이름표가 붙어 있지 않습니다.
그래서 눈이 전혀 보이지 않는 방문자가 태블릿 앞에서 혼자 끝까지 작성하기는 어렵습니다.
직원이 곁에서 돕는 절차를 함께 두시기를 권합니다.**

---

## 1. 무엇을 우리가 고칠 수 있고, 무엇을 고칠 수 없나

| 화면 | 만든 곳 | 우리가 고칠 수 있나 |
|---|---|---|
| 설정 마법사 `setup.html` | 이 상품 | 예 |
| 방명록 화면 `index.html` (머리글·감사 화면·되돌리기 알림) | 이 상품 | 예 |
| 그 안의 **문서 작성 화면** | 이폼사인 서비스 | **아니요** — 다른 회사 주소의 화면을 그대로 띄웁니다 |

## 2. 우리가 만든 부분 — 검사 결과

`node tools/check-a11y.mjs` 한 줄로 다시 확인할 수 있습니다.
(끝 코드 1 = 심각도 serious 이상 위반이 남아 있음)

| 화면 | 고치기 전 | 고친 뒤 |
|---|---|---|
| `setup.html` (6단계를 모두 펼친 상태) | 위반 3종 · 77곳 (`aria-allowed-attr` critical, `landmark-one-main`, `region`) | **0** (적용 완료) |
| `index.html` 기본 화면 | 위반 1종 (`meta-viewport` critical) | **0** (아래 ※) |
| `index.html` 되돌리기 알림이 뜬 상태 | 위반 1종 (`meta-viewport` critical) | **0** (아래 ※) |

※ `index.html` 의 고침은 같은 시각 다른 작업이 이 파일을 쓰고 있어 **아직 반영 전**입니다.
고칠 내용은 `.work/patch-index-a11y.md` 에 조각 단위로 적어 두었고, 사본에 적용해 측정한 결과가
「0」 입니다. 반영 전까지 `node tools/check-a11y.mjs` 는 `index.html` 의 `meta-viewport` 하나 때문에
끝 코드 <span class="nb">1</span>로 끝납니다.

원문 결과 파일:

| 파일 | 내용 |
|---|---|
| `reports/a11y-axe.json` | 지금 이 폴더 상태 그대로의 검사 결과 |
| `reports/a11y-axe-before.json` | 고치기 전 상태의 검사 결과 |
| `reports/a11y-axe-index-patched.json` | `index.html` 고침까지 적용한 사본의 검사 결과(위반 0) |

### 넣은 것

- **화면 구조**: 「본문으로 건너뛰기」 링크, 큰 영역 표시(머리글·단계 바로가기·본문·맺음말),
  제목 차례 <span class="nb">1 → 2 → 3</span>을 어긋나지 않게 맞춤.
- **입력칸**: 모든 칸에 이름표를 붙이고, 칸 밑 도움말을 그 칸의 설명으로 이어 붙임
  (화면 낭독기가 「빈 화면 방치 되돌리기(초), 로비나 전시 부스는 60~90초를 권합니다」처럼 이어서 읽습니다).
- **상태 알림**: 주소를 읽어 낸 결과, 복사 완료, 「안 돼요」 판정, 설치 진행 단계를
  화면 낭독기가 스스로 읽도록 표시(`role="status"` · 오류는 `role="alert"`).
- **설치 단계 접었다 펴기**: 단계 머리글을 버튼으로 바꾸고 펼침 상태를 알림
  (`aria-expanded` · `aria-controls`). 끝낸 단계도 다시 펼쳐 볼 수 있습니다.
- **화면 그림**: 그림마다 「무엇이 보이는 화면이고 빨간 표시가 어디인지」를 글로 적음.
  예 — 「Vercel 새 프로젝트 만들기 화면. 이름 칸이 이미 채워져 있고, 아래쪽 검은 Create 버튼에 빨간 표시가 있습니다.」
  빨간 네모 자체는 꾸밈으로 처리하고(`aria-hidden`), 같은 내용을 그림 밑 글로 함께 전합니다.
- **크게 보기 창**: 대화상자로 표시, <span class="nb">Esc</span>로 닫기, <span class="nb">Tab</span>이 창 밖으로 새지 않도록 가둠,
  닫으면 원래 자리로 되돌아감.
- **기기 종류 탭**: 좌우 화살표로 옮겨 다닐 수 있게 함.
- **키보드**: 화면의 모든 조작(80곳)을 Tab 만으로 지날 수 있고, 이름이 없는 곳은 0곳입니다.
  포커스가 지금 어디 있는지 파란 테두리로 보입니다.
- **터치**: 누르는 자리를 모두 44×44픽셀 이상으로 키웠습니다.
- **움직임**: 기기에서 「움직임 줄이기」를 켠 사람에게는 애니메이션과 스르륵 넘어가는 스크롤을 끕니다.
- **글자 확대**: <span class="nb">200%</span>로 키워도 가로 스크롤이 생기지 않습니다(폭 720픽셀 상당에서 확인).

## 3. 이폼사인 작성 화면 — 실제로 열어 본 결과 (우리가 고칠 수 없는 영역)

<span class="nb">2026-09-16</span>에 실제 작성 주소를 헤드리스 크롬으로 열어 측정한 사실입니다.
**고쳐 달라고 요청할 수는 있어도 이 상품 쪽에서 고칠 수는 없습니다.**

| 확인한 것 | 결과 | 근거 |
|---|---|---|
| 페이지 언어 표시 | **있음** (`lang="ko"`) | 최상위 문서 |
| 제목 차례 | **어긋남** — `h1` 다음에 `h3` 가 나옴 (axe `heading-order` moderate) | 동의 화면 |
| 화면 확대 | **막혀 있음** — `user-scalable=no, maximum-scale=1.0` (axe `meta-viewport` **critical**) | 이폼사인 페이지의 설정 |
| 작성 틀(iframe) 이름 | **없음** (axe `frame-title` serious) | `id="viewer_frame"` 에 `title` 없음 |
| 「계속」 버튼 색 대비 | **기준 미달** (axe `color-contrast` serious, 비활성 상태) | `#agreeButton` |
| 동의 체크상자에 <span class="nb">Tab</span>으로 도달 | **가능** | Tab 순서에 있음 |
| 동의 체크상자의 이름 | **있음** — 「전자문서 및 전자서명 사용에 동의합니다.」 | `<label>` 연결됨 |
| <span class="nb">Space</span>로 동의 체크 → 「계속」 활성화 | **됨** | 누른 뒤 버튼의 `disabled` 가 풀림 |
| 「계속」 눌러 작성 화면 진입 (키보드) | **됨** | <span class="nb">Tab → Enter</span>로 도달·실행 |
| <span class="nb">Tab</span>으로 작성 틀 안 입력칸까지 도달 | **됨** — <span class="nb">13~17번째 Tab</span>에서 `#dp…`, `#ozinput_20~23` 에 차례로 들어감 | Tab 순회 기록 |
| **작성 칸의 이름(무엇을 적는 칸인지)** | **없음** — 보이는 입력칸 8개 중 5개가 이름 없음. `#ozinput_20~23`, `#dp…` 모두 `aria-label`·`<label>`·`title` 없음 | 프레임 안 전수 조사 |
| 서명 자리 | **`canvas`에 `tabindex=0`만 있고 `role`·이름 없음** (20×20 6개, 341×102 1개) | 프레임 안 전수 조사 |
| 서명 입력창을 키보드(Enter·Space)로 여는 것 | **판정 보류** — 눌러도 서명 메뉴·서명 팝업이 뜨지 않았으나, **대조군인 실제 마우스 클릭으로도 뜨지 않았다.** 검사 방법의 한계이므로 「안 된다」로 단정하지 않는다 | 키보드 7회·실제 마우스 클릭 7회 모두 변화 없음 |
| 서명 메뉴 자체(서명/이니셜/도장 입력) | 링크로 되어 있어 **포커스는 갈 수 있음** (`<a href="javascript:void(0)">`). 다만 서명 자리를 눌러 메뉴를 띄우는 것이 먼저다 | 최상위 문서 |
| 「전송」 버튼 키보드 도달 | **됨** — 2번째 Tab, 이름 「전송」 | Tab 순회 기록 |
| 화면 낭독기(NVDA) 실제 청취 | **미실측** — 이 검사 환경에서는 화면 낭독기를 돌릴 수 없다. 위 판정은 모두 **구조 증거**(이름·역할 유무, Tab 순서)에 근거한다 | — |

### 이 표가 뜻하는 것

키보드로 **돌아다닐 수는 있습니다.** 그런데 작성 칸에 이름이 없어서,
화면 낭독기는 「편집」이라고만 읽고 **그 칸이 성명인지 연락처인지 방문 목적인지 알려 주지 못합니다.**
서명 자리도 마찬가지로 이름과 역할이 없습니다.
이것은 WCAG 4.1.2(이름·역할·값) 에 어긋나는 상태입니다.

## 4. 그래서 전맹 방문자가 혼자 작성할 수 있나요

**터치 태블릿에 아무도 없는 상태로 두면, 혼자서는 어렵습니다.** 이유는 두 가지입니다.

1. 위에서 본 대로 **작성 칸에 이름이 없어** 무엇을 적는 칸인지 알 수 없습니다.
2. 무인 태블릿에는 보통 **화면 낭독기가 켜져 있지 않습니다.**
   방문자가 직접 켤 수 있는 기기도 있지만, 키오스크 잠금(앱 고정·가이드 접근)을 걸면
   설정 화면으로 나갈 수 없어 켜는 것 자체가 막힙니다.

### 현장에서 이렇게 보완하세요

- **직원 호출 수단을 곁에 둡니다.** 태블릿 옆에 「도움이 필요하면 눌러 주세요」 버튼이나
  안내 데스크 연결 벨을 두고, 점자·큰 글씨 안내판을 함께 붙입니다.
- **대신 작성하는 절차를 마련합니다.** 직원이 방문자에게 항목을 소리내어 읽어 주고
  구술한 내용을 대신 입력한 뒤, 방문자 동의를 받아 서명을 받습니다.
  누가 대신 적었는지 기록에 남기시기를 권합니다.
- **되돌리기 시간을 넉넉히 둡니다.** 「복귀 카운트다운」 기본값 5초는 짧습니다.
  눈이 잘 보이지 않거나 글을 읽는 데 시간이 걸리는 방문자가 오는 곳이라면
  **20초 이상**으로 두세요(설정 마법사 4단계에서 바꿉니다).
  「빈 화면 방치 되돌리기」와 「작성 중 이탈 되돌리기」도 함께 늘리시는 편이 좋습니다.
- **종이 기록부를 함께 둡니다.** 화면 작성이 어려운 방문자를 위한 대체 수단입니다.

## 5. 다시 검사하는 방법

```bash
cd kiosk-product
node tools/check-a11y.mjs                 # 이 폴더를 임시로 띄워 검사
node tools/check-a11y.mjs <올린 주소>    # 이미 올려 둔 주소를 검사
```

- 결과 요약은 화면에, 원문은 `reports/a11y-axe.json` 에 저장됩니다.
- 심각도 serious 이상 위반이 남아 있으면 끝 코드 <span class="nb">1</span>로 끝납니다.
- `frame-tested`(수동 확인)는 늘 남습니다 — 이폼사인 작성 화면은 다른 회사 주소라
  검사 도구가 그 안으로 들어갈 수 없기 때문입니다. 그 안쪽 사실은 위 3번 표에 적었습니다.
